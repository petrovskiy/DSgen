# ДИЗАЙН-СИСТЕМА

> Этот документ — источник истины по визуальному оформлению проекта.
> AI-агенты ОБЯЗАНЫ следовать этим правилам при создании или изменении UI.
> Не изобретайте визуальные стили, противоречащие этому документу.

---

## 🧭 ИНСТРУКЦИЯ ДЛЯ АГЕНТА-ЗАПОЛНИТЕЛЯ

> Этот блок предназначен для агента, который заполняет шаблон конкретными
> данными проекта. При финальной генерации документа для пользователя
> этот блок нужно удалить.

Правила заполнения:

1. **Не оставляй плейсхолдеры пустыми.** Если данных для поля нет — не изобретай значение произвольно, а выведи его из уже заданных решений (direction, keywords, ближайший аналог из раздела 8 «Дизайн-паттерны» или другого заполненного поля).
2. **Направление (Design direction) должно физически подтверждаться токенами.** Если direction содержит слова вроде «неоновый», «футуристический» — в разделах Shadows и Color обязаны появиться соответствующие glow/яркие акценты. Если direction — «тёплый минимализм» — shadows должны быть мягкими/почти отсутствующими, а не neon glow. Расхождение между разделом 1 и разделами 3/9 — ошибка заполнения, а не вариативность.
3. **Не дублируй первое ключевое слово в строке "Направление дизайна".** Строка формата `[слово1] / [слово2] / [слово3] / [слово4]` не должна начинаться с одного и того же слова дважды (например, `Технологичный / Технологичный / Холодный / Точный` — ошибка генерации, а не стиль).
4. **Каждый цвет из Palette должен использоваться хотя бы в одном компоненте.** Неиспользуемые цвета — сигнал, что либо палитра раздута, либо токены компонентов заполнены не до конца.
5. **Primary и Primary Hover/Active не могут совпадать.** То же для любых пар default/hover, default/active — иначе интерактивность визуально не считывается.
6. **Text Primary не должен по умолчанию совпадать с Primary (акцентным) цветом**, если явно не обосновано в разделе 28 «Текущие решения». Акцентный и основной текстовый — разные роли, их слияние ломает переиспользуемость токена при ребрендинге.
7. **Text Secondary не должен совпадать с Accent/Primary.** Та же логика, что и в правиле 6, но для вторичного текста — иначе весь второстепенный текст в интерфейсе визуально читается как ссылки/кнопки.
8. **Disabled bg/text — одно значение, используемое одинаково везде.** Значение, которое указано в разделе 3 (`Text Disabled`) и в состоянии `Disabled` компонента (раздел 10), обязано быть одним и тем же токеном. Не описывай disabled-состояние в двух местах разными числами.
9. **Промежуток (gap) в разделе 6 должен быть числом, равным `grid-gap` из раздела 5.** Если значения разошлись — это ошибка заполнения, а не намеренная вариативность между разделами.
10. **Паддинги в разделе 14 (Mobile / Tablet / Desktop) не должны убывать с ростом брейкпоинта.** Mobile ≤ Tablet ≤ Desktop. Если desktop-паддинг меньше mobile — заполнение ошибочно.
11. **В разделе 9 (тени) значения SM/MD/LG должны визуально отличаться друг от друга.** Если LG равен MD дословно — либо добавь настоящее третье значение элевации, либо явно укажи в разделе 28, что в системе используется только 2 уровня теней, и убери третью строку.
12. **В разделе 18 (визуальные эффекты) указывай только реально включённые эффекты**, каждый — с конкретным CSS-свойством и списком селекторов, где он применяется (см. формат раздела 18 ниже). Не перечисляй выключенные эффекты как «НЕТ» — просто не включай их в документ. Каждый эффект, упомянутый здесь, обязан быть отражён в реальном коде компонентов (components.md), иначе не указывай его.
13. **Заполняй все состояния, а не только Default.** Для Button/Input — обязательны hover, focus, disabled как минимум; error и loading — где применимо.
14. **Если чего-то не хватает** — следуй протоколу из раздела 24: посмотри существующие компоненты → существующие токены → ближайший паттерн → консистентность важнее новизны.
15. После заполнения прогони чек-лист валидации в разделе 26.1 — это не опционально.

```text
xl:  [значение]
2xl: [значение]
3xl: [значение]
4xl: [значение]
```

## Отступы для layout (паддинги контейнера, gap сетки)

```text
container-padding: [значение, 16–32px]
grid-gap:          [значение, 12–32px]
```

> ⚠️ Это отдельная шкала от вертикальных отступов выше. Не подставляй сюда значения из вертикальной шкалы (md/lg/xl) — паддинг контейнера и gap сетки должны оставаться в диапазоне 12–32px независимо от того, насколько крупная базовая единица вертикального ритма.

## Правила

* Для вертикальных отступов между секциями используй большую шкалу (md–4xl).
* Для горизонтальных паддингов и gap используй layout-шкалу (12–32px).
* Отдавай предпочтение токенам отступов, а не произвольным значениям.
